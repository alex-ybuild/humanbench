# Contributing to HumanBench

A guide for adding questions, personas and scoring changes without breaking the 7 language builds, saved progress or old share links. The Chinese writing briefs in `i18n/new/BRIEF_*.md` are still the final word on tone and length limits. This file explains how the machinery fits together.

## 1. How the app is put together

No framework and no bundler. `build.py` inlines five scripts into one HTML page. They load in this order and share globals:

| File | What's in it |
|---|---|
| `bank.js` | `ROWS` (benchmark table), `AA` (leaderboard), `POOLS` (scored questions), `PERSONA_AXES` / `PROFILES` / `PERSONA_Q` (persona system), `SLOP_VIBES`, `VIBES`, `TRAITS`, `RUN_PLAN`, `CHARTS` / `UIS` (inline SVG/HTML for chart and computer-use questions) |
| `chats.js` | `CHATS`: multi-turn "iconic moment" dialogue trees |
| `arc.js` | ARC-style grid puzzles. Answers and decoys are generated by rule functions, never hand-written |
| `lv4.js` | Boss (lv4) questions plus later expansion rounds, all appended to existing pools |
| `app.js` | Everything else: run assembly, adaptive difficulty, scoring, persona matching, result page, share cards, Jev, telemetry |
| `deploy/src/worker.js` | Cloudflare Worker: static pages, `/r/<code>` share pages, OG images, `/api/e` telemetry into D1 |

Other languages: `i18n/<lang>/{bank,chats,arc,lv4}.js` are **full translated copies**, matched to the Chinese files **by position**. UI strings in `app.js` are translated by Chinese fragment through `i18n/<lang>/ui.json` (`i18n/ui_tool.py`). Traditional Chinese (`tw`/`hk`) is generated from Simplified by `i18n/tw_sync.py` on every build, so don't edit those by hand. Use `i18n/tw_fix.json` / `hk_fix.json` for corrections.

## 2. One run, start to finish

1. `buildRun()` (`app.js:63`) turns the 76 slots in `RUN_PLAN` (`bank.js:2010`) into items. Persona, vibe and chat items are drawn up front. **Scored (ability) questions are drawn only when you reach them**, so difficulty can adapt.
2. `targetLevel()` (`app.js:98`) looks at your last 6 answers: ≥80% right → lv3, ≥50% → lv2, otherwise lv1. lv4 (Boss) needs ≥84% plus a recent lv3+ hit, and never shows before Q20. ARC is drawn one level harder.
3. `pick()` (`app.js:312`) records `{row, ok, half, fun, lv, pts, secs, issue, ...}` in `S.log`. The first correct answer among ability questions 2–9 triggers the "are you sure?" sycophancy test.
4. Chat, persona and vibe choices add **traits** (`S.traits`), **axis values** (`S.axSum/axN`) and **flavor** (`S.flavor[modelId]`, which records which model's signature line you picked).
5. `release()` (`app.js:921`) builds the result page, cards, captions and share code.

## 3. Scoring rules (what you'd optimize)

**Parameter count.** Each ability answer earns `pts = score × LV_VAL[lv]`, where `score` is 1 for correct, 0.5 for `half`/`fun`, and 0 otherwise. `LV_VAL = {1:.7, 2:.85, 3:1, 4:1.15}` (`app.js:58`). θ is the mean of `pts`. `tierOf(θ, misses)` (`app.js:754`) maps θ onto the 16-step `LADDER` (`app.js:737`) with a piecewise-linear curve: steep up to θ=0.6, flatter after that. **∞ / "suspected AGI"** needs θ ≥ 1.02 **and** ≤ 2 real misses. The AA score is interpolated from the ladder.

**Benchmark row.** `rowScore()` (`app.js:800`) is the mean `pts` for that row, capped at 1, times a speed factor of 0.94–1.0. Elo rows map to 1150–1890.

**Architecture.** `archOf()` (`app.js:767`): the `dense` pool is a "Dense check" where one question tests 2–3 domains. At most one miss gives Dense. Otherwise ≥30B gives MoE. Expert count depends on size, and the active ratio depends on Dense accuracy. **Context window** comes from your longest correct streak.

**Persona.** `personaResult()` (`app.js:852`) scores each profile `p` as

```
s = 1.2·z(flavor[p]) + 1.0·weighted-mean z(traits in TRAIT_TO[p]) − dist(axes, p.v)/60
```

`z()` standardizes against `PERSONA_BASE` (`app.js:819`), which holds mean/sd from live players. That makes the result "what's unusual about you" rather than "what you picked most". The hidden **human** persona requires ≤1 flavor pick, ≤1 negative trait, and a `based` z-score above 1.

**Simulating changes.** Run `node qa/sim.cjs [runs]` before and after any scoring or content change. It uses `qa/headless.cjs` to load the **real** game code in Node (`buildRun`, adaptive `drawAbility`, `tierOf`, `archOf`, `personaResult`), plays whole runs, and prints two tables. The first is the persona distribution for several answer styles (random, warm, based, chaos, syc, or `flavor:<model id>`). The second is the size distribution for players of ability A. Since it loads `app.js` directly, it can't drift from the game.

```bash
node qa/sim.cjs 4000                              # default: all styles, A = -1..3
STRATS=random,flavor:Kimi node qa/sim.cjs 4000    # does a Kimi-leaning player become Kimi?
LANG_DIR=i18n/en node qa/sim.cjs                  # simulate with the English bank
```

Simulated players are not real players, so compare distributions **before and after** a change instead of reading them as live rates. `qa/topend.cjs` is a faster, parameterized re-implementation of the size curve, meant for trying settings through `CFG='{…}'` without editing `app.js`. Its defaults match the live rules.

## 4. Invariants: never break these

- **Append only.** Question, chat, persona and option **indexes** are stored in saved progress, saved results, cross-language relocalization (`relocalize()`), and share links. Never insert, reorder or delete existing items. Add new ones at the end. To retire a chat, add it to `RETIRED_CHATS` instead of removing it.
- **Every language has the same structure.** Same counts, same order, same flags (`ok/half/fun/meme/lv/halluc/id/tr/ax/go/end`) and node names. `node qa/validate_lang.cjs <lang>` enforces this.
- **Model ids are never translated.** `id: "豆包"`, `"GPT-5 系"`, `"Claude"`… stay as they are in every language. Display names come from `id_name` in `i18n/langs.json`.
- **The correct option is never the uniquely longest one**, in every language.
- **Share-code compatibility.** `ti` is a ladder index (16 = AGI), `b[]` follows the order of `ROWS`, and `pi` is a persona id. Changing `LADDER` length, `ROWS` order or persona ids breaks old PK links.

## 5. Adding questions (the usual contribution)

Work in a new expansion **round** (for example round 4) so everything lands in its own appended block:

1. **Write the Chinese draft** as `i18n/new/zh4_<name>.js`. The name decides where it goes: `chats*` → `chats.js`; `persona*` / `vibes*` / `slop*` → `bank.js`; anything else → `lv4.js`. Keep the variable names from round 3 (`ADD3`, `ADD3_CHATS`, `ADD3_PERSONA`, `ADD3_SLOP`, `ADD3_VIBES`, `ADD3_CHARTS`, `ADD3_UIS`). Each file is wrapped in its own function, so the names don't clash.
   ```js
   const ADD3 = { traps: [
     { lv: 2, q: "Question", issue: "≤20-char known issue for the share card", opts: [
       { t: "right answer", ok: 1, r: "why it's right" },
       { t: "plausible wrong", r: "roast" }, { t: "…", r: "…" }, { t: "…", r: "…" },
     ] },
   ] };
   ```
   Read `i18n/new/BRIEF_ADD3.md` (scored questions) and `BRIEF_NEW.md` (chats, persona, slop) first, and `EXISTING*.md` so you don't repeat an existing joke.
2. **Check it:** `node qa/add3_check.cjs zh4_<name>.js` must print `OK`. For chart or UI questions, also run `node qa/add3_preview.cjs zh4_<name>.js` and look at the screenshots.
3. **Translate** into `en4_`, `ja4_`, `es4_`, `ko4_`, `fr4_<name>.js` with the same structure (see `BRIEF_TR3.md`). Check each against the Chinese: `node qa/add3_check.cjs en4_<name>.js --zh zh4_<name>.js`.
4. **Merge** each language: `python3 i18n/new/merge3.py zh 4`, then `en 4`, `ja 4` and so on. Re-running replaces the block in place.
5. **Build and verify:** `python3 build.py`, then `node qa/validate_lang.cjs <lang>` for en/ja/es/ko/fr. Open `index.html` to play it.

New items join the random pools automatically. Scored questions are picked by `lv`, so fill the thin spots first. Current counts:

| Pool | Items | lv1/2/3/4 | Slots per run |
|---|---|---|---|
| chart | 19 | 4/8/6/**1** | 4 |
| osworld | 27 | 11/8/7/**1** | 5 |
| traps | 49 | 22/15/**8/4** | 6 |
| persona (per axis) | **6** | – | 1 per axis |

Persona questions repeat the fastest: each run takes one per axis from only 6.

## 6. Adding a persona type

A persona touches many places. Missing one fails quietly.

1. `bank.js` `PROFILES`: **append** `{id, name, nick, glyph, color, v:[W,D,V,T,X,C], line, roast}`. Do the same in every `i18n/<lang>/bank.js` (`id`, `v` and `color` must match).
2. Give it a **flavor model id**, for example `"Qwen"`, and tag real signature lines with it: `id: "Qwen"` on options or `E(title, text, "Qwen")` on endings. It needs enough of these (roughly 15–30 across chats, slop and persona) to be reachable.
3. `app.js`: `FLAVOR_TO` (model id → persona id), `TRAIT_TO` (stereotype traits), `THEMES` (card colours), `makeCaptions` voice line, `personalNames` → `byFlavor`, and `PERSONA_RATE` if you want a rarity label.
4. **`PERSONA_BASE.fl.<id>`.** Without it, `z()` falls back to mean 0 and sd 0.5, so a single pick scores z=2 and the new persona **swallows everyone else**. Seed a realistic baseline from the tag counts (existing personas sit around mean 0.03–0.66, sd 0.2–0.7). Check with `node qa/sim.cjs` that the new persona is reachable (`STRATS=flavor:<id>`) and doesn't dominate `random`. Then have the maintainer recalibrate with `qa/persona_calib.py`, which needs the live D1.
5. The Chinese strings you added to `app.js` need entries in each `i18n/<lang>/ui.json`. `python3 i18n/ui_missing.py` lists what's missing.
6. `i18n/langs.json` → `id_name` if the model id should display differently in some language.
7. Add the new id to the `IDS` sets in `qa/add3_check.cjs` and `qa/new_check.cjs`.
8. Layout: the persona dex is a **3×3 grid** (8 + hidden). A 10th cell needs CSS work in `index.html` (`.dex-grid`, `.c4-dex`).

## 7. Adding a benchmark row

This means changing `ROWS` (4 opponent values), `POOLS.<id>`, `SECTION_LABEL`, `EXPERT_NAME` (`app.js:766`), `pkBench` if the name is long, and `RUN_PLAN` slots. The total of 76 appears in UI copy, every `ui.json`, and the worker text. Append the row at the end of `ROWS` so the `b[]` arrays in old links still line up.

## 8. Known issues and starter tasks

- **Model tags on dialogue options don't count as flavor (open, needs a decision).** In chat and persona trees, only the *ending's* id (`E(..., id)`) adds to `S.flavor` (`renderTree`, `app.js`). The 127 option-level `id:` tags (for example `id: "DeepSeek"` on a chat reply) are only used for the "because you said…" quote. The writing briefs assume they add flavor. Counting them is a one-line change, but `PERSONA_BASE` was calibrated from live data *without* them. Changing only the code moves the simulated distribution a lot (hidden human for "based" players drops from 17.6% to 8.2%, Grok and Kimi rise). It has to ship together with a recalibration (`qa/persona_calib.py`, which needs the live D1), or the tags should be treated as quote-only and the briefs updated.
- `"Qwen"` (2 chat endings) has no persona, so it appears in the flavor bar only. That's by design unless someone adds a Qwen persona (§6). `"GPT-5"` endings now map to the GPT-5 persona.
- `qa/persona_sim*.cjs`, `persona_cal.cjs` and `persona_base.cjs` still use the old run assembly and are kept only as history. Use `qa/sim.cjs`.
- Telemetry doesn't record which answer was picked for each question, so `lv` is set by hand. Logging `(itemTag, ok)` would allow real difficulty calibration (IRT/Rasch) instead of the mean-of-points θ.

## 9. Windows notes

- Use `python` if `python3` is the Microsoft Store stub.
- `tw_sync.py` and `merge3.py` write LF line endings on every platform, so a build doesn't touch tracked files. If `git status` shows data files as modified after a build, check line endings first.
- Without esbuild (`npm i -D esbuild`) the build skips comment stripping and prints a note. That's fine locally. `NOSTRIP=1` silences it.
